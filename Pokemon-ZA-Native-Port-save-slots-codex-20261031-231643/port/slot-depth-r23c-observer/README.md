# r23c process-once startup option, preserving the r23 protocol

This is an isolated copy of the frozen r23 observer. The production changes are the new `slot-startup.inc` and three lines in `observer-r23c.c`: its include, initialization before the capture opt-in check, and its frame callback before that check. Runtime, client, protocol, shared header and r21c capture-retirement helper remain unchanged.

`/app0/slot-depth-options.txt` accepts exactly `8`, `16`, `8\n` or `16\n`. The helper opens this fixed path read-only with NOFOLLOW and NONBLOCK. A bounded POSIX read loop consumes at most four bytes in at most four calls, accepts positive partial reads, requires EOF and checks close status. Any negative read, including EINTR, fails safely without retry. Four bytes are always invalid. Missing, invalid or unreadable configuration selects the code default 8 without calling the switch API. Configuration is read once per process, even if observer initialization is repeated.

A configured 16 remains pending until a positive, submitted, non-represented frame outside the full sample-buffer lifetime. One attempted call to the existing checked runtime API consumes it before the call; a rejection is final and leaves the runtime fallback unchanged. This path works with capture disabled. It never reads config, queries status or switches during settling or recording. The attempt frame skips ordinary mailbox polling, capture and measurement arming. Subsequent frames retain the earlier observer behavior. No startup receipt files are written. Errors reset and capture errno immediately around each call; a read failure retains source=read_error even when close also fails, and both failures are logged. The r23b hardware attempt stayed at 8 with source=read_error; its aggregate log does not prove which stdio stage failed. This isolated r23c helper avoids FILE internals and still needs fresh native verification.

Startup logs are `[za-r23c-startup] config requested=8|16 source=file|missing|invalid|open_error|read_error|close_error` followed by raw `open_result/open_errno/read_result/read_errno/read_calls/bytes/eof/close_result/close_errno` fields (uncalled results are -2), and one optional `[za-r23c-startup] apply requested=16 result=... confirmed=0|1 active=... frame=... status_frame=... status_result=... cost_ns=... budget_valid=... pool=... largest_free_extent=... driver=... required=...`. Confirmation requires the same coherent actual-16, exact frame/result, completed drain and valid memory bounds as the existing observer receipt. The largest free extent is contiguous memory, not total free RAM. Runtime switch diagnostics remain available separately.

Run `bash test.sh` in WSL Ubuntu. It executes the actual observer twice under ASan/UBSan: all inherited regressions, then startup-specific process emulation and actual measurement/queued-command tests. It also runs the unchanged client tests and verifies frozen protocol/client/retirement hashes. Test fixtures explicitly reset startup statics to emulate a new process; no production reset does so. Host tests do not replace the parent's fresh native startup verification.

This directory extends the finalized r22 observer with one scoped command, `slot_depth 8` or `slot_depth 16`. Runtime integration, resource allocation and GPU lifetime policy are owned separately by `port/slot-depth-r23`; this directory contains no runtime implementation or console operations.

The observer permits a switch only after a successful non-represented present with a positive frame. Menu, failed-present, represented and frame-zero calls are rejected without invoking the runtime. While settling or recording, neither commands nor slot status are polled. Existing preparation, immutable-span, submission, capture, retirement, FPS, input and continue paths remain available. The native retirement helper and its tests are byte-identical to finalized r21c via r22.

`slot-depth-control.h` is the shared ABI1 contract. `za_slot_depth_switch` returns 8 or 16 only when that depth is applied; -1 invalid input, -3 unsafe boundary/drain, -4 memory gate, -5 incompatible other experiment, and -6 resource preflight failure. The runtime owns serialization, the checked drain, baseline8/capacity16, and the batch4/preparation-baseline/immutable-off restriction. The status getter copies one coherent executor-locked snapshot, with actual active depth, and performs no allocation, memory query or drain.

Receipts distinguish this request's `requested_slots`, `runtime_result`, and `frame` from the last runtime snapshot's `status_requested_slots`, `status_result`, and `status_frame`. That distinction preserves truthful diagnostics for a menu or boundary rejection, where no new runtime call occurred. Applied status requires matching request/result/frame/actual depth and completed sequence at least the drained sequence. Rejected runtime changes must retain the prior active depth.

Sixteen-slot application additionally requires `budget_valid=1`, a nonzero pool no larger than 64 GiB, `0 < largest_free_extent <= pool_bytes`, `driver_bytes <= pool_bytes`, at least 1 GiB of required headroom and a largest free contiguous extent meeting that requirement. `largest_free_extent` is not total free RAM. Eight-slot application may succeed when the budget query is unavailable. All memory/resource diagnostics are reported as their actual fields, with strict integer bounds in the client; no synthetic total is calculated.

```text
python client.py slot_depth --session SID --seq N 16
python client.py collect --session SID --seq N --slot-depth 16 --out EVIDENCE
```

Programmatic collection requires `expected_slot_depth=16` or `8` (canonical strings also accepted). The expected target is independent of the acknowledgement's echoed request. A queued, stale, malformed, incoherent or mismatched result cannot be saved as an applied result. Earlier collection arguments remain unchanged.

The inherited tests execute the actual observer parser and receipt writer with runtime status stubs under ASan/UBSan, plus the actual offline client. They cover both depths, negative statuses, memory/ABI/frame/return mismatches, replay, safe-present rejection, measurement deferral, old snapshot diagnostics, malformed acknowledgements and prior protocol regressions. Test input hashes are captured before compilation and checked again afterward. These tests do not establish runtime memory behavior or GPU correctness; the separate runtime and hardware reviews are required for those conclusions.
