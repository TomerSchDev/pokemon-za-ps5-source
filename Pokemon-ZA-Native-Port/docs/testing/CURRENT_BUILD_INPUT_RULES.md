# חובה לבדוק קלטים עדכניים לפני כל בנייה

בתוקף מיד לפי הוראת תומר מ־1 בנובמבר 2026. הכלל חל על כל פרויקטי Z-A, בכל worktree ובכל מסלול בנייה. [AGENTS הקנוני](../../AGENTS.md) ושאר כללי הפרויקט נשארים מחייבים במלואם.

**כל פרויקט עוצר התקדמות לבנייה הבאה עד שבדיקת הקלטים של אותה בנייה הושלמה.** לפני כל בנייה קוראים מחדש את [דוח התלויות](BUILD_DEPENDENCY_AUDIT.md), את [המפה](BUILD_DEPENDENCY_MAP.json) ואת המקורות העדכניים של הרכיבים הנדרשים. שימוש במחקר ישן מותר בתנאים המפורטים בהמשך; הוא אינו אישור לבנות ממנו.

זוהי חובה תפעולית של הסוכנים. המסמך והתבניות אינם guard executable, אינם משנים runner או queue ואינם מוכיחים שצ'אט אחר קיבל הודעה או נעצר. אין כאן פקודת בנייה חדשה.

## תחולה ועצירה בטוחה

הבדיקה חלה על compilation, relink, code generation, בניית helpers ב־C#/Python או שפה אחרת, יצירת mods ונתוני משחק, prepared suites, reproduction ו־packaging. מסלול data-only כפוף לכלל גם אם אינו מפעיל compiler של המשחק.

סוכן שכבר עובד מגיע ל־checkpoint בטוח, מפסיק להתחיל שלבי בנייה נוספים ושומר את מצב העבודה והראיות. אם נדרשת עצירת build לא גמור שבבעלותו, הוא עושה זאת דרך המפקח שלו ורק באופן בטוח. אין להרוג תהליך של סוכן אחר, לשנות ticket או manifest שכבר נרשמו, לגנוב lease או לעקוף את ההגנה על קונסולה מנותקת. מחקר לקריאה בלבד יכול להימשך עם רישום המקורות הנדרש.

## לפני כל build: לפתור את הקלטים בפועל

1. **לזהות את העבודה:** project/job, הפעולה המדויקת, source snapshot ופקודה מתוכננת, output חדש ומבודד ותנאי עצירה. הבדיקה מתועדת לפני התחלת הפעולה, לא בדיעבד.
2. **לזהות את המפה שנקראה:** נתיב, SHA-256 וזמן בדיקה. המפה היא snapshot תחום ולא אטומי; חתימתה לבדה אינה מוכיחה שהמידע עדיין עדכני. יש לרענן את מקורות הסמכות הנוכחיים לכל רכיב: release/component descriptor, manifest, מקור/branch מאושר או קטלוג מקומי רלוונטי.
3. **לפתור את כל הקלטים האמיתיים:** source ו־dirty/untracked overlay, objects, headers, response files, import libraries, SDK, compiler, flags, generators, schemas, tools, donors ו־base-mods לפי הפעולה. מתעדים גם environment overrides וקלטים טרנזיטיביים; נתיב ברירת מחדל בסקריפט אינו בהכרח הנתיב שנצרך בפועל. מפרידים קלט בנייה מ־provenance, reference לאימות ו־output.
4. **להשוות לבסיס הנוכחי המאושר:** לכל רכיב מציינים מזהה, תפקיד, מיקום בפועל, גרסה/חתימה, מקור סמכות ומיקום הגרסה הנוכחית. "הכי חדש" הוא הרכיב העדכני המאושר לתפקיד ול־ABI/schema/target האלה, ולא הקובץ בעל ה־mtime הגבוה ביותר. העתקה או שינוי שם של חומר ישן אינם הופכים אותו לעדכני.
5. **לסגור פערי מיפוי:** קלט חדש, caller דינמי או רכיב שאינו מופיע במפה מחייבים רישום מקור וקשר תלויות מעודכנים לפני הבנייה. אין להסיק PASS מהיעדר entry או מקיום path. אין צורך להמתין למיפוי מושלם של כל הפרויקטים; סגירת הקלטים של ה־job הנוכחי צריכה להיות מלאה ומגובה בראיות.
6. **לרשום החלטה:** קלט מיושן, זהות לא ידועה, מיקום נוכחי לא פתור או חסם הגירה שלא טופל משאירים את העבודה ב־`BLOCKED`. רק אחרי השלמת הבדיקה ניתן לרשום `READY_FOR_SCOPED_BUILD` לפעולה המסוימת. זו החלטת סוכן המבוססת על ראיות; אין דרישה חדשה לקבל אישור ידני מתומר לכל build רגיל. סמכויות אישור קיימות, ובפרט merge/promotion של main, נשארות בתוקף.

את רישום הבדיקה שומרים בתיקיית evidence מקומית של העבודה, מחוץ לקלטים מוגנים ובלי לתפוס תור PC לצורך הכנתו. [תבנית רישום](build-input-check.example.json) מתחילה בכוונה ב־`BLOCKED` ובערכים לא ידועים. ממלאים אותה מנתונים אמיתיים; אין להעתיק את הדוגמה כראיית מוכנות. שינוי מקור, קלט, מתכון או baseline לאחר הבדיקה מבטל את מוכנותה ודורש בדיקה מחודשת לפני ההפעלה הבאה.

## הגירה אינה מחייבת להוכיח תוצאה לפני שאפשר לבנות אותה

לפני build שמטרתו הגירה, בוחרים candidate מקור נוכחי שנבדק, קלטים פתורים ומקובעים, baseline controls, בדיקות regression ותנאי rollback. ניתן להכין כך `READY_FOR_SCOPED_BUILD` לניסוי ההגירה המוגדר. אין בכך אישור סופי לתוצר שטרם נבנה או נבדק. שומרים את baseline הידוע, בונים לתיקייה חדשה ומאשרים את החלופה רק לאחר בדיקותיה. אין חריג כללי שמאפשר לבנות שוב מתיקיות ישנות משום ש"צריך אותן כדי להגיר".

frozen inputs ו־SDK של release מאושר אינם פסולים רק בגלל גילם. שחזור היסטורי כ־control או rollback חייב להיות מסומן במפורש, עם profile מאושר, תכלית וראיות סמכות; הוא לא יהפוך בשקט לבסיס של candidate חדש. אין לשנות release locks קיימים או לבצע repin ל־job ממתין. החלפת baseline, flags, SDK או משמעות קלט נעשית ב־descriptor/manifest חדש ובהליך האימות המתאים.

יש לשמר את תיקון מספרי ה־JSON המתועד עבור `36b3d5d`, או יורש מאושר ומתועד שלו. `MAIN=main-1.1.0` וה־eboot הבסיסי `7d837a58` לבדם אינם מוכיחים שהתיקון נשמר. לפני עבודה חדשה קוראים את רישום ה־baseline הנוכחי; ערך שנמצא ביומן מקומי אינו בדיקת קונסולה חיה, ואינו רשות לפנות לקונסולה. מקור לא־מנוהל, wrapper ו־wrap flags הדרושים לתיקון צריכים להיכלל בסגירת הקלטים. ראו [כללי main](../../workbench/cards/main.md).

כל הכנה, הורדה, קימפול ואריזה מסתיימים לפני הרשמה לתור בדיקות PC/console או ל־`zw test`. עצירה ושחרור משאב נשארים לפי [כללי התורים](../../workbench/cards/resource-queues.md), לרבות חריג הקונסולה המנותקת. הכלל אינו מתיר בנייה בזמן החזקת תור בדיקות או התעלמות מבעל משאב אחר.

## מחקר בחומר היסטורי: חובה לדעת מה נקרא ואיפה מחפשים עדכון

מותר לקרוא שאריות, snapshots וראיות היסטוריות לצורך מחקר. לכל רכיב שעליו נשענת מסקנה רושמים:

- מזהה לוגי ותפקיד, נתיב/URI מדויק שנקרא, גרסה וזמן קריאה, וחתימה או manifest מזהה עם ציון האם נמדדו כעת או נלקחו מרשומה קודמת. אם לא ניתן לזהות תוכן בוודאות, מתעדים את המגבלה במפורש.
- node וקשר במפה, נתיב וחתימת גרסת המפה, ומקור הסמכות שנבדק כדי לאתר את המיקום הנוכחי של הרכיב.
- המיקום, הגרסה והזהות העדכניים הידועים, וקשרי `superseded_by` אל החלופות והראיות המאשרות אותן. אם המיקום העדכני לא נפתר, רושמים `UNKNOWN` ופער חוסם טענה שהמסקנה עדכנית; אין להמציא מיקום או לפרש רשימה ריקה כ"אין חדש יותר".
- המסקנות שנשענות על אותו חומר ומה צריך לבדוק מחדש אם הרכיב או מיקומו השתנו. מסקנה על חומר היסטורי נשארת מסומנת כהיסטורית עד שאומתה מול המקור הנוכחי הרלוונטי.

ראו [תבנית רישום מקור מחקר](research-source-record.example.json). נשמרת יכולת להמשיך מחקר היסטורי גם כשיש פער, אך אין להשתמש בפער כבסיס ל־build או לטעון שנבדקה הגרסה העדכנית. מסירת מסקנה לפיתוח או לבנייה מחייבת פתרון חוזר של המיקומים הנוכחיים, עדכון קשרי ההחלפה ורענון המסקנות המושפעות.

## רשימת בדיקה קצרה

- נקראו הכללים הקנוניים והמפה, ונבדקו מקורות הסמכות העדכניים של כל קלט?
- הנתיבים שנפתרו בפועל, הגרסאות, החתימות והקלטים הטרנזיטיביים מתועדים?
- כל קלט שנוסף או השתנה מופיע ברישום תלויות מעודכן, בלי חסמי `UNKNOWN` פתוחים?
- candidate הגירה ו־controls נבדקו מראש, בלי לטעון שתוצאה שטרם נבדקה אושרה?
- רישום prebuild מקומי מלא, output חדש, ובדיקות/rollback מתוכננים לפני תור בדיקות?
- חומר מחקר היסטורי קשור למקורו ולמיקום העדכני, והמסקנות רועננו כשנדרש?

## משמעות שדות התבניות

שני קובצי ה־JSON הם דוגמאות לרישום ידני, לא manifest שמתקבל ב־`zw test` ולא validator חדש. `null`,‏ `UNKNOWN`,‏ `false` ו־`BLOCKED` הם מצבי התחלה מכוונים, לא ראיות. ברישום אמיתי נדרשים timestamps ב־UTC, paths פתורים ו־SHA-256 מלא כאשר מצוינת חתימה. שדות identity מציינים גם את מקור החתימה ואת מועד בדיקתה; חתימה מוצהרת וחתימה שנמדדה בפועל נשמרות בנפרד.

`template_only` נשאר true בדוגמאות; ברישום job אמיתי מסירים את סימון הדוגמה רק אחרי שמילאו ובדקו את התוכן. `allowed_to_start` יכול להיות true רק לצד `READY_FOR_SCOPED_BUILD` עם בדיקות מלאות וחסמים סגורים. `final_candidate_validation` נשאר `NOT_RUN` עד הבדיקות בפועל, גם אם build מותר להתחיל. שדות baseline משקפים את המקור המקומי שנקרא בזמן הבדיקה ואינם מאשרים התקנה או promotion. אין לכלול ברישומים tokens, מפתחות, שמירות או תוכן משחק מוגן; כל מגבלות הרישוי, האחסון וה־NAS נשארות בתוקף.



## סיום כל בנייה מחייב ניקוי

בתכנון ה־job יש להגדיר תוצרי ביניים, תוצרים סופיים וראיות שחייבים לשמור. אחרי אימות מוצלח יש לבצע את [שלב הניקוי המחייב](BUILD_CLEANUP_RULES.md) ולרשום תוצאה, חריגי debug ושטח שנמדד. כשל build שומר את הראיות הדרושות לאבחון עד סקירה, ולא יוצר ארכיון מקומי בלתי מוגבל. אין למחוק קלט pinned או קובץ שנדרש ל־check-proof.
