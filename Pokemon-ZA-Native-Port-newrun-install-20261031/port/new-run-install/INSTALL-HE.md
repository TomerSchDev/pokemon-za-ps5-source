# התקנת מועמד לתיקון קריסה ביצירת ריצה

זהו adapter ייעודי על בסיס `main-1.1.0`, המחבר את כלי ההתקנה הקיים לחבילת תיקון פענוח המספרים. `CANDIDATE.json` מצמיד את קובץ המועמד ואת כל מקורות המתקין ב־SHA-256. הכלי אינו מעדכן את `MAIN` או מקפיא גרסה.

רק `eboot.bin` מוחלף. השמירות, הנכסים, המודים, העברית וקובצי התצורה נשמרים. קובץ התוכנית הקודם נשאר בשם ייחודי בקונסולה, וגם נקרא פעמיים ונשמר ב־NAS לפני ההתקנה.

## תנאי ההפעלה

לפני כל פעולת קונסולה צריך לקבל מ־Tomer תיאום מפורש: המשחק נשמר ונסגר, מותר להפעיל את הלאנצ׳ר הקיים לצורך גיבוי כל הריצות בתפריט ולסגור רק את אותו תהליך מזוהה, ומותר להחליף את קובץ התוכנית למועמד המוצמד. אין להסיק אישור מהזמן שחלף. העבודה הנוכחית הכינה ובדקה רק את המסלול המקומי.

אימות `plan` עובד ללא חיבור לקונסולה:

```powershell
.\zw newrun-install plan --local C:\Users\Tomer\AppData\Local\Temp\za-newrun-json-fix-state-NEW
```

לאחר תיאום מפורש, הסוכן המבצע מריץ כל שלב בנפרד ובודק את תוצאתו. `--handoff` מקבל את תשובת המשתמש בפועל:

```powershell
.\zw newrun-install init --local C:\Users\Tomer\AppData\Local\Temp\za-newrun-json-fix-state-NEW --console-ok --handoff "ACTUAL USER REPLY"
.\zw newrun-install backup --local C:\Users\Tomer\AppData\Local\Temp\za-newrun-json-fix-state-NEW --console-ok
.\zw newrun-install install --local C:\Users\Tomer\AppData\Local\Temp\za-newrun-json-fix-state-NEW --console-ok
.\zw newrun-install complete --local C:\Users\Tomer\AppData\Local\Temp\za-newrun-json-fix-state-NEW --console-ok
```

הכלי מקבל lease דרך התור המשותף, בודק SHA של הקובץ המותקן בשתי קריאות, מגבה את כל הריצות כולל `active.json` בקריאות חוזרות, ודורש שהגיבוי הסתיים בחמש הדקות האחרונות. החלפת הקובץ מתבצעת באמצעות העלאה לשם חדש, קריאה חוזרת ואימות, שינוי שם של המקור לשם rollback, הצבת המועמד וקריאה חוזרת נוספת. הקוד לביצוע הפעולות האלה הוא `port/r28b-dlc-dex/install-r28b.py`; ה־adapter אינו מממש מתקין מקביל.

אם שלב נכשל, אין להפעיל את המשחק או לשנות פינים כדי לעקוף את הכשל. יש לשמר את תיקיית הראיות ואת ה־lease לצורך בירור. אם שמירת משתמש או ה־PID/session השתנו במהלך הגיבוי, הבדיקה מסרבת לסגור תהליך או להמשיך.

בבדיקת הקריאה האחרונה אחרי הקריסה, אין תהליך משחק, אך `PPSA91762_004` עדיין מכילה `data/mnt/preinst`. הכלי הקיים מסרב להפעיל לאנצ׳ר במצב כזה; אין לעקוף זאת במחיקה. החלופה המוכנה היא: `init` בעוד המשחק סגור, ואז המשתמש פותח את המשחק המקורי ונשאר בתפריט, במסגרת אותו תיאום. הסוכן אוסף זהות טרייה של PID/session/title/active run ואת SHA קובץ התוכנית, עם לוג התחלה חדש ומוצמד. `backup --resume-menu-identity IDENTITY.json` משתמש ישירות ב־`m.backup(..., resume_identity=...)` הקיים. ה־adapter דורש זהות מהחמש הדקות האחרונות שאחרי `init`, לוג תקין ומוצמד ללא fault, והמתקין הקיים מאמת שוב את ה־PID, ה־session, הכותר, הריצה והקובץ החי. אין פקודת קלט או מחיקת sandbox במסלול הזה. קובץ הזהות הוא ראיית ביצוע, ואינו חלק מארכיון המקורות.

## בדיקת התיקון

השלמת ההתקנה מאמתת רק את החלפת הקובץ. כדי לאמת את התיקון, יש לתאם בדיקה נוספת, להתחיל `zw klog --include-backlog` לפני הפעלת המשחק, ולבקש מהמשתמש ליצור ריצה חדשה. אין להשתמש בבדיקת Continue של ריצה ישנה כתחליף לבדיקה הזאת. יש לבדוק גם שהעברית והמודים הקיימים נשמרו. אין עדיין טענת הצלחה בחומרה.

## חזרה לגרסה הקודמת

החזרה מחליפה את קובץ התוכנית בלבד, ואינה משחזרת שמירה היסטורית. משתמשים ב־`--rollback-from` עם תיקיית ראיות ההתקנה המקורית, ב־state חדש ובתיאום חדש. אותו adapter מפעיל את מתקין ההחלפה הקיים בכיוון ההפוך, אחרי גיבוי טרי של כל הריצות. הוא דורש שהקובץ המותקן הוא המועמד המדויק ושהגיבוי המקורי תואם ל־`main-1.1.0`.

```powershell
.\zw newrun-install plan --local C:\Users\Tomer\AppData\Local\Temp\za-newrun-json-rollback-NEW --rollback-from "ORIGINAL INSTALL EVIDENCE"
```

לאחר תיאום מפורש, מריצים `init`, ‏`backup`, ‏`install`, ‏`complete` עם אותם `--rollback-from` ו־state חדש; `init` דורש גם `--handoff` בפועל. שינוי קובץ התוכנית אינו מוחק ריצות שהמשתמש יצר בעת בדיקת המועמד.

אין לכלול בקובצי מקור `.lease.json`, אסימוני תור, גיבויי שמירות או עותקי משחק. כל אלה נשארים בתיקיות מצב/ראיות נפרדות.
